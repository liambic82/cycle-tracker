# Architecture and security notes

## Boundaries

- `src/domain`: date-only arithmetic, journal schema, history calculations, CSV serialization, and vault encryption. No React Native imports.
- `src/data`: ordered persistence, cross-tab edit lease, session lifecycle, fictional demo data, and platform file export/import.
- `src/ui`: shared React Native views that adapt to phone and desktop widths.
- `App.tsx`: navigation, current-day context, responsive composition, and daily editor.
- `scripts/prepare-web.mjs`: production service worker generation. Only public application assets are cached; journal contents never pass through the service worker.

## Manual sleep records (0.16.0)

Journal content is now **format 6**. Each entry has a `sleep` object: `durationMinutes` (integer 0–1440 or null), subjective `quality` (very-poor/poor/okay/good/very-good or null), and `wakings` (integer 0–100 or null). These are bounded input values, not clinical thresholds. All three fields are required in format 6; malformed types and values are rejected without coercion. Formats 1–5 migrate to all-null sleep fields, retaining their existing observations and format-5 symptom ratings. New backups require 0.16.0+. Encryption, passphrases and biometric keys are unchanged.

The record describes the user's main sleep ending on the entry's waking date, including daytime sleep. It is estimated time asleep, excluding time awake. The form holds local drafts; Save validates whole hours/minutes and wakings before one journal update. Blank hours and minutes together mean unknown; a single supplied component treats the other as zero. Cancel, leaving the editor or locking discards unsaved changes. Clear form fields changes only the draft until Save. A saved zero or quality-only record keeps its entry; whole-entry Undo copies the sleep object independently. Sleep disruption symptom labels and severity stay independent.

History uses inclusive 30/90/365-day ranges ending today, ignores future entries and shows newest records first with fixed 0–24-hour bars. Unknown duration has no bar; explicit zero has a zero-length bar and numeric text. Missing days are counted separately. There are no sleep scores, inferred stages, trends or diagnoses. CSV adds Sleep duration (minutes), Sleep quality and Night wakings after Other symptom severity and before opt-in sexual fields. The independent Sleep report section includes only recorded fields inside the selected date range. Preview and PDF use the same filtered snapshot.

Wearable import is not implemented in 0.16.0. The [Fitbit-first plan](wearable-sleep.md) requires a separate provenance-aware session model rather than treating every wearable session as a manual daily estimate.

## Symptom severity and dated history (0.15.0)

Preview 0.15.0 introduced **format 5**. Each entry adds `symptomRatings`, an array of exact saved symptom labels and integer values from 0–10. `cramps` remains authoritative for the exact legacy Cramps label; duplicate Cramps ratings in the array are rejected. Arrays avoid interpreting custom labels as object keys. Imports reject missing/malformed arrays, duplicate labels, orphan ratings and out-of-range values. Formats 1–4 gain empty rating arrays without inferring values; prior cramps, medications, doses and other observations are preserved. Format-5 backups require 0.15.0 or later; the current format-6 requirement is above. The encryption envelope, key derivation and biometric credentials are unchanged.

Selecting a symptom does not rate it. Clearing a rating retains its label; removing the label clears its rating. Zero is explicit None and remains a logged record. Whole-entry deletion copies ratings into the existing session-only Undo snapshot. Hiding a category does not change stored labels or ratings. The optional editor autosaves through the existing ordered journal writer and resets with the selected date.

`symptomSeverity.ts` also derives searchable labels from nonfuture records and inclusive 30/90/365-day histories ending today. Dated bars all use a fixed 0–10 scale, newest first. Rated dates, selected-but-unrated dates and dates without that symptom logged are counted separately. Omitted dates never become zeros and bars are not joined or interpolated. History displays 30 records at first, with more available; it does not infer symptom causes, trends, personal phase or clinical thresholds.

CSV adds Other symptom severity after Dose records and before opt-in sexual-health columns, retaining the existing cramps column. Doctor report ratings follow the same filtered labels as their Symptoms or Mood and mind section and the report date range. The same snapshot drives preview and PDF; excluded ratings leave no hidden content. Full encrypted backups include every rating; device appearance/photo/reminder choices remain separate.

## Experimental period estimates (0.12.0)

`src/domain/periodEstimate.ts` is a pure derived calculation from explicit starts and today's date. `PeriodEstimate` supplies session-only opt-in, context, and completeness review. It is a full-width Calendar subview; returning, primary navigation, Log today, locking, and Android Back exit it. Neither answers nor estimated values enter journal state, exports, notifications, or calendar cell rendering. No schema or security change is needed.

The latest seven starts within 365 days provide six complete intervals. Future starts, unsupported/variable intervals, stale or insufficient history, poor earlier-entry fit, expired results, and unsupported output dates produce named unavailable states. The median is fixed; shortest/longest dates are historical spread only. `backtestIntervals` holds each target out chronologically and compares median, mean, last interval, and a fixed-28 example on identical eligible folds; targets outside training limits remain in scoring. It never silently imputes a skipped start. See [the exact rules and validation limits](period-estimates.md).

The fictional sample now has seven starts. Existing journals and format-4 backups remain unchanged. Independent clinical and full-policy external-data validation are still pending; synthetic checks and descriptive personal-history errors are not population accuracy.

## Daily context and education (0.11.0)

`src/domain/cycleContext.ts` derives a small observation-only snapshot: selected date, latest explicit period start on/before it, elapsed days, inclusive recorded cycle day, recorded flow or unknown, and an always-unknown personal phase. Future dates return no projected values. A note, symptom, product, or medication never creates a start marker or a phase. Long gaps retain their arithmetic count with a missing-record explanation, without a menopause/late-period/ovulation inference. The daily editor no longer displays a projected cycle day on future dates.

The same module bundles nine short educational topics and public source metadata. Content is not dynamically generated or personalized from journal details. The existing encrypted `showPerimenopause` preference filters only the dedicated topic, without removing records. The library has no saved read history, new preference, schema migration, telemetry, or network fetch. All text is present in the production app bundle and browser offline shell. Source links open fixed HTTPS URLs only when tapped; no journal values are added. External pages follow their own data practices.

`CycleContext` is reachable from a calendar subview and inside the existing DayEditor sheet/card. Returning preserves the selected date and records. Topic chips scroll horizontally, and Previous/Next buttons provide a non-swipe alternative with labeled boundaries. The source section provides readable link names, external-site context, and an open-failure message. Text has no fixed-height clipping. Navigation/locking unmounts the session view; Android Back closes the full calendar context subview. In a phone daily sheet, Android Back retains the existing behavior of dismissing the sheet.

This is the education portion of milestone 5. No personal period/phase/ovulation prediction, hormone curve, symptom-cause inference, or clinical alert is added. The [source record and next prediction criteria](cycle-education.md) distinguish factual source checks from independent clinical validation. Journal content remains format 4; exports and backups keep their existing behavior.

## Doctor summaries and PDFs (0.10.0)

`src/domain/report.ts` builds a filtered, immutable text snapshot shared by the on-screen preview and PDF renderer. A report selects an inclusive date range ending today or earlier (up to 366 days), independent general sections, and four independent sexual-health fields. Notes and sexual-health fields default off every time the report screen is reopened. Only strict `true` selects a field. Excluded-only records leave no dated placeholder; explicit No/None remains distinct from unlogged. Free-text names, symptoms, and product descriptions are included with their section and are not semantically redacted; the controls explain this.

Cycle statistics use only explicit boundaries inside the requested range and retain unknown/incomplete spans. Flow counts distinguish unlogged days from explicitly no flow. Mood labels use the curated Mood & mind category; other/custom labels remain Symptoms. Since 0.15.0 both sections include their optional numeric ratings; 0.16.0 adds an independent Sleep section. Medication versions are included if they overlap the range, with the original effective date/cycle anchor as context and a clamped report interval. Dose records use their historical snapshots and journal date, with actual taken date/time shown separately. Notes require both the notes switch and the corresponding medication/dose section. No predictions, medication recommendations, adherence rate, inferred missed doses, labs, or clinical prompts are generated. Reports themselves introduced no schema change in 0.10.0; current format 6 is documented above.

`reportPdf.ts` uses `pdf-lib` and `@pdf-lib/fontkit` with bundled, SIL-licensed Noto Sans regular/bold fonts. Reports have Letter-sized pages, repeating headers, range/page-number footers, wrapped prose and long tokens, and preserved blank lines. Selected snapshot size is limited to 200,000 JSON characters and layout to 200 pages; exceeding either returns an explicit error rather than truncating. Unsupported glyphs also stop export without changing saved records. Latin/Greek/Cyrillic coverage is present; emoji and broader script support remain future work. Text is selectable, but PDFs are not tagged for accessible reading order yet.

`src/data/reportExport.ts` loads packaged fonts through Expo Asset; browser service-worker assets now include TTF files. It creates a browser PDF download or a native cache file followed by the OS share sheet, with a readable-data warning in the preview. An unmounted report cannot open a share sheet after generation completes. Native temporary PDFs live only in the dedicated `cycle-report-exports` cache directory and are removed after sharing/cancellation; startup and the next export also clear that directory to recover from process termination. Copies deliberately saved to another destination remain outside the encrypted journal and are not deleted by the app. Device sharing/cancellation and offline font access still require hardware verification. PDFs contain no attachments, JavaScript, or external font references.

`metro.config.cjs` resolves `tslib` through its legacy package entry because the 1.x import wrapper used by pdf-lib otherwise fails under Metro's ESM/CommonJS interop at runtime. Other packages retain Expo's normal resolution. The Android build helper copies this configuration into its short-path cache. This was found by running the actual browser export after bundles and Node tests passed; browser download verification is required alongside build checks.

References: [PDFDocument API](https://pdf-lib.js.org/docs/api/classes/pdfdocument), [PDFFont API](https://pdf-lib.js.org/docs/api/classes/pdffont), [Expo Metro customization](https://docs.expo.dev/guides/customizing-metro/), and [bundled font attribution](../assets/fonts/README.md).

## Local medication reminders (0.9.0)

`src/domain/reminders.ts` derives a bounded queue from enabled medication definitions and recorded dose outcomes. Daily, weekday, on/off, placebo, future dated changes, and pauses reuse the medication domain. As-needed plans have no dose alerts. Taken/Skipped/Taken late all suppress the corresponding medication/time occurrence; deleting a record can restore a still-future alert. Multiple medications due at the same instant share one generic notification, retained while any occurrence remains unrecorded. No dose names, amounts, health notes, record IDs, or vault keys enter notification content or identifiers.

The queue contains at most 60 distinct dose times over 30 local calendar days, one refresh notice, and one separately requested test notification. The UI displays its refresh deadline. A refresh notice is scheduled one minute before the first omitted occurrence or the end of the horizon. This bounded design avoids treating an encrypted, locked journal as background-accessible and leaves space below iOS's pending-notification limit. It is not indefinite scheduling: users must unlock by the visible deadline. A paused/PRN-only routine queues no renewal notice; a scheduled plan beginning beyond the horizon can still request renewal.

Dates are constructed from each local calendar date and wall-clock time, not by adding 24-hour intervals. JavaScript Date's spring-gap normalization moves a nonexistent time forward; fall-overlap times fire once at the first occurrence. Existing queued timestamps retain their original absolute time during travel until the journal is unlocked. Unlock, foreground return while unlocked, and manual refresh replace native requests even when their identifiers match, recovering alarms that Android force-stop may have removed. A minute timer while active and saved journal changes reconcile only differences. The UI explains time-zone refresh and potential phone/battery delays. DST/time-zone arithmetic has automated coverage; OS and device behavior still need hardware tests.

`ReminderService` serializes scheduling, opt-in changes, test delivery, and cleanup. A schedule is persisted successfully before it is handed to the OS. Latest-save revision guards prevent obsolete save callbacks from scheduling after deletion. Lock saves and finishes reminder reconciliation before dropping session data; the service keeps no journal/key between operations. Enabling requests native permission only on an explicit user action, and checks Android channel blocking. Permission denial or revocation leaves the journal usable. A partial native failure clears owned requests and raises a separate reminder error, not a false “queued” status. Off/restore/erase operations clear pending and presented app reminders, including the test, before declaring completion. A failed cancellation stays visible/retryable. Backup validation precedes replacement cleanup, so an invalid backup does not disable an existing journal's reminders.

Device-local opt-ins live separately at `cycle-tracker.reminder-opt-ins.v1`, containing only the public vault salt and opaque medication IDs. They never enter the journal or encrypted exports. Another vault's or malformed preferences are cleared. Restore resets choices even when restoring the same vault. Journal content remains version 4 and the existing encrypted envelope/key remains unchanged. The phone OS necessarily stores generic text and scheduled timestamps outside the encrypted vault. The app name may be visible in system UI; notification content never exposes which medication is due. No direct Taken/Skipped action bypasses journal unlocking.

The native adapter uses [Expo Notifications](https://docs.expo.dev/versions/latest/sdk/notifications/) `~57.0.22`, date triggers, stable IDs, an Android private-visibility channel, and foreground presentation. No push token registration, server, account, or background decryption is used. The Android dependency supplies notification and boot permissions. This preview does not request special exact-alarm access: the inspected SDK uses `setAndAllowWhileIdle` on Android 12+ without it, so alerts may arrive after the requested time. Boot/package-update rescheduling is supplied by the native library, pending device confirmation. The browser adapter neither imports the notification runtime nor prompts for browser permissions. Sample mode never calls the real reminder service.

## Journal rules

Dates are local calendar keys (`YYYY-MM-DD`), not midnight UTC timestamps. Cycle intervals use UTC day numbers to avoid daylight-saving errors. A new cycle requires an explicit period-start marker. Changing flow to none or spotting clears that day's start/end markers. Bleeding duration requires a recorded end before the next period start. Unfinished cycles have no inferred length.

## Calendar and visual history (0.5.0)

Entries include `flowRecorded`. Choosing any flow option sets it to true; explicitly choosing None is a saved observation. Clearing flow sets it to false, removes period boundaries, and retains other daily details. An otherwise empty unlogged entry is removed. On import, older positive-flow and spotting entries infer true; older None entries infer false because previous versions did not distinguish an explicit choice from the default. Inconsistent or malformed flags are rejected. This change originally retained journal format 1 in 0.5.0; see the 0.8.0 migration below for the current format. CSV's eighth column remains `Flow recorded`; newer columns are appended after it.

Year, month, and day views share the journal's selected date. Annual month tiles open a continuous month calendar without changing selection; selecting a date opens the editor. Miniature dates are visual context within a single accessible month button, not tiny individual touch targets. The daily view has previous/next controls and a full editor; compact month view retains its daily sheet. Calendar labels show recorded cycle-day counts only through today. There are no prediction overlays.

History statistics use all recorded cycles and exclude unknown lengths/durations. Charts show the latest twelve cycles oldest to newest with date, year, numeric value, and accessible labels; an incomplete value is a dash, not zero. Bleeding duration is the inclusive span from period start to the first recorded end within the same cycle, not a claim that every intervening day had bleeding. History rows initially show twelve cycles, with an option to reveal older rows.

Each chronological flow strip ends before the next start or at today. It distinguishes bleeding, spotting, explicit None, and missing flow observations, with accompanying text counts. Notes or symptoms alone do not supply flow information. Sparse dates become compact runs so long gaps do not generate a UI element per day. Cycle-day lookup uses sorted starts; history scans sorted entries once for end markers.

## Symptom catalog and preferences (0.4.0)

`src/domain/symptoms.ts` contains 99 curated choices covering all four symptom reference lists in the source brief. Compound source items are split where useful (for example oily/dry skin), while all 30 original labels remain unchanged. Search includes a small set of alternate terms. Categories describe browsing organization, not a diagnosis; selecting a symptom called Spotting or Skipped periods does not create flow or cycle markers.

Entry symptom arrays remain strings. Unknown/imported labels are retained. Search and selection compare trimmed, case-insensitive identities without rewriting saved values; existing custom labels take precedence over new catalog matches in the browser. Curated categories and user-created labels stay distinct. Logging is capped at 200 symptoms per day, including custom labels, matching backup validation; adding a definition and logging it fail together at the limit. New custom definitions retain the 100-label limit, while older valid imports remain readable.

The 0.4.0 journal format introduced `preferences.showPerimenopause`, retained in current journals. Imports without preferences default to `true`; a supplied malformed preference is rejected. This preference lives inside the encrypted snapshot and encrypted backups, not separate plain storage. Hiding the curated category affects its browse/search choices only: selected symptoms remain in the daily summary, CSV, and backups, and custom labels remain available even if their wording overlaps that category. Sample preferences remain session-only. The vault envelope, passphrase, and biometric key do not change.

The daily editor shows selected symptoms and compact quick choices. Its symptom browser replaces the editor content within the existing phone sheet or desktop card, so there is no second native modal. Changing views resets the parent scroll position. Checkbox/pressed states are explicit for browser accessibility as well as native accessibility state. Native keyboard, Android Back, large text, and TalkBack behavior still require device checks.

## Product records and bleeding observations (0.6.0)

Journal **content version 2**, introduced in 0.6.0, added `productRecords`, `clots`, and `flooding` to each entry. Version 1 journals migrate to empty product arrays and null observations without inferring anything from flow, notes, or symptom labels. Versions 2 and 3 require valid product/observation fields; unsupported future versions and malformed records are rejected. Earlier apps reject newer content versions rather than silently discarding new details on restore/save. Update all receiving apps before moving a new backup. The encrypted envelope remains version 1 and uses the existing passphrase and biometric key.

Product records have stable IDs, a type (pad, tampon, cup, disc, period underwear, liner, other), an action (used, changed, or emptied), a whole quantity, optional local `HH:MM`, optional product description, and optional observed collected mL. Emptying and collected amounts apply only to cups/discs. Amounts are totals for that record, not automatically multiplied by quantity or converted from product counts. The preview supports up to 100 records per day, quantities 1–100, 60-character descriptions, and amounts 0–1,000 mL to two decimal places. These are input/storage bounds, not clinical thresholds. Blank times and amounts remain null; zero is an explicit amount. Records display by local time, with untimed records last; no timezone conversion or current-time default is applied to historical records.

Clots and flooding independently use null (not logged), false (No), or true (Yes). Either explicit observation or a product record keeps the day logged even without flow. They never infer bleeding intensity, period boundaries, or cycle statistics. Clearing flow does not remove them. Whole-entry deletion/Undo includes all new fields and deep-copies product records in the Undo snapshot.

Flow details replace the editor content inside the existing sheet/card. Observation choices autosave. Product forms explicitly require **Add record** or **Save record changes**; Cancel discards their local draft. Date/view changes or locking may discard an unsubmitted draft. Removing a product is behind its options menu and confirmation, with local Undo until leaving flow details or another removal. Undo appends that record by ID and never replaces another record; the daily record limit still applies. Sample records and changes remain in memory only.

CSV retains its first eight columns and appends `Clots noticed`, `Flooding noticed`, and `Product records`. Blank observations mean unlogged; Yes/No remain explicit. Product records are readable newline-separated descriptions within one quoted cell, containing time/unknown time, type, action, quantity, description, and any collected amount. IDs are internal identities and not included in the readable export. Encrypted backups retain every structured field and ID.

## Flooding explanation and sexual-health records (0.7.0)

The owner approved the visible definition beneath **Flooding noticed?**: “A sudden gush of heavy menstrual bleeding, which may overwhelm your period products and leak onto clothes or bedding.” It draws on [NHS England's heavy-period decision aid](https://www.england.nhs.uk/wp-content/uploads/2023/11/PRN00250-dst-making-a-decision-about-heavy-preiods.pdf) and [NHS Devon's heavy-period information](https://myhealth-devon.nhs.uk/my-condition/condition/heavy-periods/). The copy explains the logging term without assigning a diagnosis, volume estimate, or clinical threshold. This source check is not an independent clinical review of the app.

Journal **content version 3** adds `sexualHealth` to each entry: nullable activity and orgasm booleans, nullable intensity (`gentle`, `moderate`, `intense`), and nullable libido (`none`, `low`, `moderate`, `high`). Versions 1 and 2 migrate to all-null sexual-health fields; current content requires all four valid fields. Explicit false/none counts as a recorded observation. No field infers another, flow, period boundaries, or cycle statistics. Choosing Not logged clears only that field, and clearing flow preserves these details. Whole-entry deletion/Undo deep-copies the sexual-health object along with other entry data.

The optional editor replaces content within the existing phone sheet, Day view, or desktop card. Choices autosave and use field-specific accessible labels and pressed states. Returning to the daily entry shows only “Details logged for this day,” without repeating the values. New encrypted backups contain all fields and require app 0.7.0 or later; legacy backups still open. Envelope version 1, key derivation, passphrase, and biometric credentials are unchanged.

Readable CSV keeps its original eleven columns. Four separate switches opt into appended `Sexual activity`, `Activity intensity`, `Orgasm`, and `Libido` columns in that order. Each new export starts with all switches off; choices are temporary UI state, not journal preferences. Only explicit `true` enables a column. A date with no general entry data and no selected sexual-health observation is omitted, so excluded fields do not leave a dated empty row. Null remains blank; No/None remains explicit. Notes and symptom labels still export unchanged, including any sexual-health wording the user entered; the confirmation explains this limitation. CSV selections never affect encrypted backups or the saved journal. PDF report controls remain future work.

## Medication schedules and dose records (0.8.0)

Journal **content version 4** adds a top-level `medications` list and `doseRecords` to each entry. Versions 1–3 migrate to empty lists without extracting or inferring a plan from notes or symptoms. Version 4 requires valid new fields; future versions are rejected. New backups require 0.8.0 or later. The encrypted envelope remains version 1; no KDF, passphrase, protected biometric credential, or preview screenshot behavior changes.

`medications.ts` is a pure domain model; `medicationActions.ts` applies validated changes to immutable journal snapshots. Each medication has a stable ID and an ordered list of dated plan versions. A plan stores its own name, medication/supplement kind, dose label, notes, local times, and schedule. Schedules may be daily, selected weekdays, repeating on/off days, as needed, or paused. An on/off cycle starts with on days on the effective date; a new version starts its own cycle. Off days have no planned doses unless the user enters an off-day label, including a placebo label for their own pack. No clinical default regimen, dose conversion, automatic titration, or medication-effect interpretation is supplied.

Dates use the existing local calendar keys and UTC day differences; times are literal local `HH:MM` without timezone conversion. Daily/weekday/cycle plans allow 1–8 unique times. On/off day counts are each 1–366. As-needed and paused plans have no scheduled times; as-needed use is offered separately and may be logged more than once per day. Schedule expansion is on demand and never creates journal entries. Storage bounds are 100 medications, 100 versions each, and 200 dose records per day; these are application limits, not medical recommendations.

The initial plan can start in the past. Later changes must start today or later, on or after the latest version, and after any existing dose record for that medication. A latest unused version can be replaced on the same effective date to correct a draft mistake; otherwise a new version is appended. Pausing is another dated version, and resuming adds a later active version. No hard-delete medication action is provided. The UI shows current/future plans and lets the user inspect history. Broader retrospective schedule editing is deferred until it can reconcile existing logs explicitly.

Dose records contain self-contained snapshots of the medication name/kind, plan ID, planned dose and time, cycle phase, user-selected Taken/Skipped/Taken late, actual amount/date/optional time, and a note/reason. Unknown time is null. Skipped records have no actual amount/date/time; as-needed records require Taken and have no scheduled time. No threshold infers late or missed status. Actual date may differ from the scheduled journal date (for example an overnight dose); it must not be in the future when recording. New records resolve the active dated plan, reject stale targets, and prevent a second scheduled record for the same medication/time/day. Editing changes only outcome fields, preserving the original plan snapshot. Import validates snapshot contents independently of current definitions so deletion/Undo and later plan corrections cannot make historical records unreadable.

`Medications` is a new primary tab. The daily journal links to `DoseLog` inside its existing phone sheet/Day view/desktop card. Plans and doses are explicit-save drafts; navigating away or locking discards unsubmitted forms. Recorded doses have an options menu, editing, removal confirmation, and local Undo. Whole-entry removal/Undo includes deep copies of dose records but retains medication definitions. Missing logs do not create flow, period boundaries, or adherence claims. Sample medication names, schedules, and dose records are fictional and session-only.

The daily CSV retains its original eleven columns and appends `Dose records` before any opted-in sexual-health columns. It includes only recorded outcomes, with readable planned/actual details and notes; it does not manufacture skipped rows for scheduled-but-unrecorded doses. A separate confirmed readable CSV includes every plan version with its effective date, exclusive next-version boundary, dose, schedule, and notes. Both use formula-prefix neutralization and CSV quoting. Encrypted backups always contain all definitions and records. Medication reminders and configurable doctor PDFs are not implemented in this preview.

## Encrypted vault format 1

The envelope contains format/version, fixed KDF parameters, a 16-byte random salt, a 12-byte random nonce, and hex-encoded authenticated ciphertext. The cipher is AES-256-GCM from `@noble/ciphers`. PBKDF2-SHA256 (`@noble/hashes`) uses 600,000 iterations and produces a 32-byte key. Additional authenticated data binds ciphertext to the application format. Every save uses a fresh nonce from Expo's `getRandomValues`; the development helper with a weak-random fallback is intentionally not used.

Journal content enters AsyncStorage only as encrypted snapshots. A non-secret reference is also stored when biometric unlock is enabled; the optional protected key is stored separately as described below. The in-memory key is overwritten on lock; JavaScript garbage collection does not guarantee erasure of every historical string or memory copy. Passphrases are not persisted. Incorrect keys, modified ciphertext, unsupported KDF parameters, and invalid journal structures are rejected. Restore input is limited to 8 MB and validated before replacement. The UI requires explicit replacement acknowledgment when a local journal exists.

Writes are serialized. A failed write is reported in the UI and keeps the edited in-memory journal available for retry or backup. Locking attempts to save before releasing the key. On web, a Web Locks lease prevents simultaneous unlocked editors on the same origin. Other origins and other devices are independent until an explicit restore; there is no sync implementation.

The background view is obscured and a one-minute background interval triggers locking, including a resume-time check when the operating system suspends timers. Native startup configures screen capture before mounting the journal or passphrase form. Store builds use `FLAG_SECURE` on Android; the installed React Native modal inherits that flag. iOS also enables Expo's app-switcher blur. Failure presents a retry screen without journal content. The browser retains its visibility overlay but cannot block screenshots.

At the owner's request, 0.5.2 preview builds allow screenshots and recordings for testing, including setup and sample mode. `app.config.ts` sets `extra.allowPreviewScreenshots` only when `APP_VARIANT=preview`; production/default builds explicitly set false, and missing runtime flags retain capture prevention. The startup hook calls `allowScreenCaptureAsync` for that opt-in. Android's secure-window Recents blanking is therefore also off in previews; the existing background overlay and one-minute lock remain, and iOS retains its separate app-switcher blur. Settings describe the preview behavior. Actual screenshot, Recents, and fold behavior remain native-device checks.

The shared passphrase field adds independent show/hide buttons with 48-pixel targets, accessible action labels and pressed states. Setup, confirmation, unlock, and restore start hidden. Busy submission immediately masks input and disables its eye button; clearing a field, changing form mode, or backgrounding hides it again. Visibility is local UI state and is never saved in the journal. Toggling changes masking only, preserving the controlled value and existing passphrase validation. Native keyboard/cursor behavior and TalkBack need hardware checks.

## Passphrase calculation (0.5.1)

Creation, passphrase unlock, and backup restore inject a platform key derivation function into the same vault implementation. Android API 26+ uses the local `modules/cycle-crypto` Expo module: Kotlin dispatches work to `Dispatchers.Default`, and a small Java helper calls the platform `SecretKeyFactory` with `PBKDF2WithHmacSHA256`. Browsers use `crypto.subtle` PBKDF2. iOS and Android API 24–25 retain the portable Noble implementation until their native paths can be validated. All paths use the same 600,000 iterations, 16-byte salt, 32-byte key, and exact UTF-8 passphrase bytes without trimming or normalization. AES-GCM, envelope version, passphrase, and biometric credential formats are unchanged.

Only key calculation has a 30-second deadline. A timeout returns an error before journal creation/replacement; a result arriving later is wiped and cannot open a session or initiate a save. Persistence is not raced against a timeout. Temporary input/output buffers are wiped where owned; this does not guarantee erasure of all runtime or bridge copies. Setup shows the current stage and elapsed time for longer operations. The timeout does not impose a deadline on storage operations or OS prompts.

The native helper's fixed compatibility vectors cover ASCII, Unicode/emoji/NUL, decomposed Unicode and whitespace, and long passwords with replacement characters. `scripts/check-android-kdf.mjs` compiles the actual Java helper and runs these vectors on the desktop JDK; the Node suite compares Noble and Web Crypto against the same fixtures and checks old/new backup interoperability. These checks cannot establish Android provider performance or bridge behavior on a physical phone. The build script copies the local modules into its short-path cache and Expo autolinks the Android module. This custom module requires the standalone preview; Expo Go is not the Android validation target.

References: [Expo asynchronous native functions](https://docs.expo.dev/modules/module-api/#asyncfunction), [Android SecretKeyFactory algorithms](https://developer.android.com/reference/javax/crypto/SecretKeyFactory).

## Biometric convenience unlock (0.3.0)

Biometrics are opt-in from an unlocked real journal and absent from sample mode's controls. `expo-secure-store` holds a small versioned payload containing the existing 32-byte derived key, vault salt, and a random activation token. Every native read/write uses `requireAuthentication: true` and a dedicated authenticated-only keychain service. Android uses an authentication-bound Keystore cipher with `BIOMETRIC_STRONG`; iOS uses the current biometric set with `WHEN_PASSCODE_SET_THIS_DEVICE_ONLY`. No fingerprint/face template or passphrase is stored by this app. A successful OS prompt is necessary to retrieve the protected credential; there is no separate prompt followed by an unguarded stored key.

AsyncStorage receives only `{ version, salt, token }` after secure storage accepts the key. Unlock requires a matching local opt-in reference, matching payload, and successful authenticated vault decryption. It cannot use a stale key from another vault or a leftover iOS Keychain entry without the current reference. Cancellation retains the setting for retry. Missing/invalidated credentials are cleared and direct the user to their passphrase; damaged or mismatched payloads never open a session. The fixed secure slot also allows explicit cleanup of interrupted setup and reinstall remnants. If cleanup fails, the UI reports the failure and preserves passphrase access.

Disabling, new-journal creation, validated backup restore, and whole-journal deletion remove the protected credential and reference before proceeding. A failed backup passphrase does not change either. If subsequent journal persistence fails after cleanup, biometric access may be off while the original vault remains; passphrase access is preserved. Encrypted backups retain the existing portable vault format and never include the biometric credential/reference. The SecureStore config plugin excludes its preferences from Android backup/device-transfer rules; the app also retains `allowBackup: false`.

An actual background transition invalidates an in-flight unlock, wiping the returned key instead of opening the journal. An iOS authentication prompt's brief inactive state is distinguished from backgrounding. A lock request during a settings/storage operation is deferred until it finishes, so a lengthy prompt does not discard the existing background-lock request. Browser builds use a separate adapter with no SecureStore import or biometric persistence.

These controls do not protect against a compromised OS or someone whose biometrics are already enrolled on the device. Native prompt behavior, enrollment invalidation, and app lifecycle integration require device tests; mocked protected storage tests are not a substitute for them. See [Expo SecureStore documentation](https://docs.expo.dev/versions/latest/sdk/securestore/) for platform behavior and limitations.

## Exports and recovery

Encrypted backups can restore on another supported platform with the same passphrase. There is no server-held recovery key, account, or password reset. A readable CSV export needs a separate explicit action and neutralizes spreadsheet formula prefixes. Native export/import cache files are cleaned up after use. File-sharing completion, dismissal, and access behavior must be checked on the target Android devices.

Daily deletion is behind the date header’s **Entry options** disclosure (0.5.3), available only for an existing entry on today or a past date. Delete opens a dated confirmation with a prominent **Keep entry** choice and an outlined red destructive action. Cancel, deletion, and opening the symptom browser close the disclosure; changing dates remounts the editor. The normal form footer contains autosave guidance and the current persistence status, including saving/error states; sample mode explicitly describes session-only changes. The mobile sheet also retains its header status.

Deleting a day removes all of that entry's fields and recalculates derived history. Undo appears near the entry header immediately after deletion. Only the most recently deleted entry is retained in memory for Undo; locking, dismissal, another deletion, or writing a new entry on that date clears it. Undo never overwrites a newer entry. The Undo record is not serialized into the vault or backups.

Whole-journal deletion requires an unlocked real journal and typing `DELETE`. The writer rejects new saves immediately, drains previous writes (including failed ones), and removes only the vault storage key. Successful deletion clears the session key, journal, Undo record, and web edit lease. Failure reopens the writer for retry/backup and retains the in-memory journal. This is logical app-storage deletion, not a guarantee of forensic erasure of flash storage or historical memory copies. Exported backups/CSVs and journals on other devices/origins remain separate. The sample journal cannot invoke whole-vault deletion.

There is no change-passphrase UI yet. Android automatic OS backup is disabled in app configuration; iOS backup policy still needs review before a store release.

## Appearance preferences (0.13.0)

`appearance.ts` defines nine palettes, twelve stable artwork IDs, light/dark tokens, and a strictly validated version-1 preference schema. `AppearanceStore` persists only `version, palette, mode, background, visibility` at `cycle-tracker.appearance.v1` in AsyncStorage. These are non-sensitive local preferences, available before unlock, separate from the encrypted format-4 journal, backup envelope, biometric reference, reminders, CSV, and PDF. No URL, photo, health record, or credential is accepted. Version 0.14.0 allows the `personal` background selector but stores its encrypted image separately. Journal restore/deletion leaves color/mode choices intact and removes the personal image; Reset appearance removes the image and restores default choices.

An external-store subscription supplies a shared React theme. Writes are ordered, UI saving/errors reflect the latest write, failed queues can recover, and unreadable/future settings fall back visibly to defaults without blocking journal access. Controls wait for preference loading. Sample mode gets an independent in-memory copy and never persists its changes; exit restores device preferences. Entering sample mode during initial loading adopts saved preferences once loading finishes.

All twelve unchanged approved PNGs are statically required from `assets/backgrounds` for offline native bundling; the review masters and SHA-256 manifest remain under `docs/design/backgrounds`. The decoration is centered/cover-cropped, bounded to its container, non-interactive and hidden from accessibility. It appears only in unlocked, unobscured content. Plain/zero visibility removes it; image-load failure falls back to the palette background. Text, navigation, and records retain opaque surfaces. Light/dark semantic flow colors are independent of the selected palette; meanings, labels, and recorded data do not change.

System appearance is the default. React Native's Appearance API uses `unspecified` to release a native override; explicit Light/Dark updates native chrome and themed inputs/status bars. `expo-system-ui` enables Android automatic appearance. Web uses a native HTML range for mouse/touch/keyboard control; installed platforms use the SDK-compatible native slider. No hosting or theme purchase service is involved.

References: [Expo color themes](https://docs.expo.dev/develop/user-interface/color-themes/), [Expo SystemUI](https://docs.expo.dev/versions/latest/sdk/system-ui/), [Expo slider](https://docs.expo.dev/versions/latest/sdk/slider/).

## Personal-photo backgrounds (0.14.0)

The approved single-image flow uses Expo DocumentPicker on native and a browser file input on web. It requests JPEG/PNG only, without broad library access. Before decoding, byte/header checks bound input to 12 MiB, 32 megapixels and 8192 pixels per side. The native Expo image loader normalizes orientation; browser `createImageBitmap` uses `from-image`. Pixels are resized/re-encoded with Expo ImageManipulator or a local canvas. The long side starts at at most 1600 pixels, stepping down to 1200/900/640/480/320 until output fits 512 KiB. JPEG quality is 0.82; PNG preserves alpha. HEIC, GIF, SVG, videos, remote URLs, crop controls and photo editing are outside this slice.

After orientation and re-encoding, a format parser discards JPEG APP/COM blocks and PNG ancillary metadata, preserving required codec/pixel and PNG transparency chunks. Trailing payloads are removed. The application stores no original filename, library path, EXIF/GPS metadata, thumbnail or photo URL. Choosing a photo creates only a draft preview; Apply makes it active. Cancel/navigation/locking aborts late results and clears owned byte arrays. An explicit cancel control also handles browsers that do not emit file-picker cancellation. Once applied, the centered cover crop uses the existing visibility control and opaque reading surfaces.

`PersonalBackgroundStore` owns one encrypted slot at `cycle-tracker.personal-background.v1`. A separate AES-256-GCM key is derived from the unlocked vault key and salt with HKDF-SHA256 and context `cycle-tracker:personal-background:v1`; this context is also authenticated additional data. Each save uses a new cryptographic 12-byte nonce. Only version, vault salt, nonce and ciphertext are serialized. The 512 KiB payload cap keeps the hex envelope near 1 MiB, below Android AsyncStorage's per-row limit; device/browser total quotas can still reject a write. A rejected replacement leaves the previous stored/displayed image intact and gives a retryable message. Invalid/corrupt/foreign-vault images fall back to plain with a recoverable error; they do not prevent journal unlock.

Photo writes/removals are ordered. Lock clears the derived key and visible URI, and session epochs prevent an older asynchronous operation from restoring the image into a later/locked session. An already accepted Apply can finish its encrypted storage write after lock; the new image is read only after the next unlock. Creation, validated restore and whole-journal deletion drain earlier photo writes before removing the slot. Wrong-passphrase/invalid restores leave it alone. Cleanup failure stops replacement/deletion; if image removal succeeds but a later journal operation fails, the photo stays removed and can be selected again. Reset also removes the copy before resetting preferences. Selecting built-in art retains the saved personal image for **Use saved photo**. Sample mode never reads or writes the real photo slot and starts with no personal image.

Native picker and image-manipulator output files exist briefly in the app-private `DocumentPicker` and `ImageManipulator` cache directories. Each file is removed in a `finally` block before a prepared preview returns; an interrupted process may leave temporary copies until next startup. Startup removes those dedicated SDK cache directories before mounting native journal content, with visible retry on failure. Only app-private cache paths are accepted for cleanup; the user's original is untouched. Web processing uses in-memory File/bitmap/canvas data and data URIs, with no upload or application-created plaintext image file. Decoder memory, OS file-provider caches and logical storage deletion are not promises of forensic erasure.

Photos appear only in unlocked, unobscured content, and are excluded from the journal schema, encrypted backups, CSV and PDF. Journal format remains 4, with unchanged passphrase and biometric credentials. Android OS backup remains disabled; iOS native backup policy and device validation remain release work. Native orientation, picker cancellation, temp-file cleanup and resource use require the new hardware checks.

References: [Expo DocumentPicker](https://docs.expo.dev/versions/latest/sdk/document-picker/), [Expo ImageManipulator](https://docs.expo.dev/versions/latest/sdk/imagemanipulator/). The installed SDK's native cache locations and orientation-loading code were inspected; browser orientation was exercised with a synthetic EXIF fixture.

## Release work

`app.config.ts` selects a separate native preview app identity when `APP_VARIANT=preview`. The Windows build script produces an ARM64 release APK from a dedicated short-path build cache and signs it with a private preview key outside Git. A Gradle guard prevents this signing configuration from being used with the store identifier. This separates test installations and credentials from a future public release; it does not replace device or security validation.

The cryptographic libraries are established implementations; this app's integration has not received an independent security audit. Review lifecycle behavior, import handling, key recovery UX, native backup behavior, accessibility, browser storage limits, and performance before real health data or public release. No remote service has been provisioned.
